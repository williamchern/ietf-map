# IETF 文稿地图 · 产品与设计说明

> 文档路径：`/workspace/docs/PRODUCT_DESIGN.md`
> 版本：v0.8（登录门、按账号隔离本机数据、账号管理）

## 一、产品定位

**一句话**：把「我关心的 IETF 草案/标准」钉到它所属的工作组/研究组上，形成一张可度量「知识缺口」的活地图。

**不做什么**（边界，也是法律与产品边界）：
- 不复制、不镜像 IETF 的全文文档内容；只做**元数据 + 短摘要 + 指向 ietf.org 的链接**。
- 不代替 IETF 官方渠道（Datatracker 是权威源）；所有状态以 Datatracker 为准，本应用只是「视图」。
- 不抓取非 IETF 来源信息（项目约束 1）。

## 二、我替你补上的「没考虑周全」的维度

你原始设想有三层：**资产（文稿）→ 容器（WG/RG）→ 关联 → 缺口分析 → 报告**。这套骨架是对的，但真正做成可用产品，下面 8 个维度缺一不可：

### 1. 容器不只是 WG/RG，还有「跨组结构」
IETF 的组织层级是 `Area → WG / RG → Document`，此外还有 BOF、Directorate、Program、IAB/IESG 等实体，以及**已关闭（concluded）组**。只挂 WG/RG 会导致：
- 一个草案换组（adoption/transfer）后地图断裂；
- Area 级空白看不出来（"整个 ROUTING 区我只关心 3 个组"）。

→ 设计上：`Area` 是一级筛选维度；组支持 **active / concluded / bof** 三态可切换；每份文稿保留 **历史归属组**（`历史容器`），不只当前组。

### 2. 文稿不是离散点，是「版本流 + 状态机」
草案有 `-00 → -18`、过期（expired）、被接纳（adopted）、成为 RFC、被废弃（replaced/obsoleted）、进入 IESG 评估（I-D last call / IETF last call / approved）、进入 RFC 编辑队列。
只存一个链接，你无法回答「我关注的这份是活的还是死的」。

→ 设计上：每条资产记录 `类型 / 最新版本 / 状态 / 标准化层级 / 流域 / 更新时间`，并用**状态颜色**（活/僵/死/标准）在地图上呈现。

### 3. 关系是双向的、有权重的
IETF 的引用关系（`normatively references` / `informatively references` / `updates` / `obsoletes` / `became RFC`）是天然的图谱边。全量有 **59 万条**，直接画会糊成一团。

→ 设计上：**只画一跳邻居**（聚焦节点的引用/被引/更新/废弃），加上**权重**（被引次数 = 该文稿的「枢纽度」，是重要度的客观代理）。密度控制靠「度数阈值」滑块。

### 4. 「缺口」必须可量化，否则只是感觉
你说「哪些地方还有欠缺」——这是产品的核心价值，但必须有定义。我给了 5 种可计算的缺口指标：

| 缺口类型 | 定义 | 为什么重要 |
|---|---|---|
| **孤儿草案** | 属于我关注组，但不在我的收藏里 | 组是热的，我却漏了 |
| **空心组** | 我关注了该组，但该组 0 收藏 | 名义关注，实际没读 |
| **断链** | 收藏 A 规范引用了 X，但 X 不在收藏 | 读懂了结论，没读依据 |
| **未覆盖区** | 我关注组密布的 Area 里，我 0 关注的兄弟组 | 视野盲区 |
| **过时风险** | 收藏的草案已 expired / 被 obsoletes / 被 replaces | 知识在腐烂 |

### 5. 报告要能定时产出，而不是手动点
「生成分析报告」如果只是点一下出一页 HTML，用完即弃。
→ 设计上：报告 = **快照**（带生成时间、数据版本），可**导出 Markdown / 打印 PDF**，并在「自动化」里配置**每周一 09:00 自动生成**（真正运行依赖部署端定时任务；雏形里给出可复制的 cron 配置）。

### 6. 多用户 / 隐私的取舍
地图 = 个人知识资产，天然私密。
→ 采用 **本地优先（local-first）**：数据在浏览器 IndexedDB，可导出 JSON 备份、可导入。早期决定不做账号系统，
也就不收集任何个人信息（这同时是 GDPR / 个保法上的最省事方案）。

v0.8 起加了**登录门**，但这条原则没变，只是补上了一层「谁能打开这个实例」的栅栏：

- 账号存在服务器上（`state/users.json`），**内容数据仍然只在本机 IndexedDB**，按账号名分库隔离。
- 服务器只知道：账号名、角色、密码散列、上次登录时间。不知道你收藏了什么、读了什么。
- 密码用 PBKDF2-SHA256（21 万轮 + 随机盐）散列，不可逆；会话是无状态签名 Cookie，HttpOnly，30 天有效并随访问自动续期（连续 30 天不来才失效）。
- 为什么还是加了：一个部署在公网的单用户工具，如果谁都能打开，就等于把「这台机器上存了什么」对所有人开放；
  而多人共用时又需要各看各的收藏。登录门正好同时解决这两件事，且不引入数据库。
- 代价：忘密码需要别人重置（或服务器上跑 `python3 auth.py reset`）；多设备要各登一次。

### 7. 移动端 + 离线是刚需（PWA 的真正理由）
开会现场（IETF 会议网络糟糕）、通勤路上读草案——**离线可读 + 可添加**才是 PWA 的价值。
→ Service Worker 预缓存应用外壳与数据快照；离线时照样能浏览、收藏、打标签，联网后同步。

### 8. 数据新鲜度必须可见
离线快照会陈旧。
→ 每个页面显示 **数据版本（快照日期）**；「配置页」提供「检查更新 → 拉取最新快照」入口；报告里写明数据截止时间，避免拿旧数据做决策。

### 补充：三个容易被忽略的小维度
- **笔记**：收藏一个草案时，最该记的是「我为什么收藏它 / 我关心的具体 § 章节」。没有笔记，三个月后地图就退化成书签堆。→ 每份资产支持 `笔记` + `主题标签`。
- **主题标签是第二套坐标系**：组是 IETF 自己的分类，主题是**你的**分类（如「QUIC 迁移性」「后量子」）。两套坐标叠加，才能看出「跨组的知识线」。
- **"可能相关"推荐**：这也是你自己提到的。实现靠两条：①同组未收藏 + 高被引；②共享引用邻居（协同过滤的极简版）。并明确标注**推荐理由**，可解释、可拒绝。

## 三、可用性收口（v0.4）

v0.3 把「关系」讲清楚了，但用起来还有四处摩擦，这一版只解决摩擦，不新增概念。

| 问题 | 改法 | 为什么这样改 |
|---|---|---|
| 图谱只占三栏中间那一小块，节点挤在一起看不清 | 画布右上角加 **⛶ 全屏**：整页放大到视口，左栏清单收起、右栏详情保留；Esc 退出。全屏后自动重新取景，节点半径在屏幕上封顶，放大也不会变成大方块 | 看图是"要看清楚"，不是"要有张图" |
| 点亮一个节点后想换一个，得先取消 | 指针状态机统一在 `pointerup` 的 `finally` 里复位；点另一个节点直接换过去。另加「只看这篇与它的邻居」把图收窄到一支 | 探索是连续的，不该有"先退出再进入" |
| 收藏库/帮助里的表格在窄屏上字挤在一起 | 所有表格统一包一层横向滚动容器；收藏库改为固定列宽，窄屏收起次要列（v0.7 起不再需要「放大」） | 宁可横向滚，也不要把信息压成看不清的一团 |
| 顶栏 6 个横排标题，切换要一个个找 | 换成左上角**视图下拉**：按钮显示当前视图，点开竖排菜单 | 视图只有 6 个，但不需要一直占着一行 |
| 诊断页有评分、报告、导出、历史快照 | 全部砍掉，只留一张按优先级排的待办清单：① 引用了没读 ② 组里有没收 ③ 过期 ④ 名义关注；每行给"为什么"和一个「收藏」 | 报告是给别人看的；这一页要解决的是"我现在补哪几份" |
| 查路径的「计算」按钮像是没反应 | 去掉按钮，改成**输入即算**（260ms 防抖）；只有一端有内容时明确说"还差终点" | 空输入点按钮没有任何反馈，等于坏按钮 |

> 一次只给一个动作：诊断页每行只有「收藏」；图谱每屏只有一个主视图；收藏库每行只有「管理」一个入口。

### 3.1 第二轮打磨（v0.4.1）：让图"真的能看"

第一轮把功能补齐了，但把截图摊开看，图本身还有三处硬伤——都跟**取景**和**力的量纲**有关。

| 现象 | 根因 | 改法 |
|---|---|---|
| 节点带着标签被画布边缘切掉，全屏时尤其明显 | 取景在物理还在抖的时候就做了，落点比当时的包围盒更外扩；`fit()` 的留白也没算分组带和标签 | 物理停稳（`alpha<=0`）后再收一次尾；留白量算上带子外扩与标签；边距随画布自适应（手机 26px / 桌面 104px） |
| 一进全屏，图先抖两下、几秒后自己跳位 | 全屏时给 `alpha` 加了 0.45 重新加热，布局全跑一遍 | 全屏只做重新取景，不重新加热——布局早就稳定了，换视口不该重算 |
| 两组的分区带经常压在一起，或者图被拉成一根竖条 | 组心间距用的是画布尺寸的固定比例（`0.32*min(w,h)`），与内容大小无关；而且两组一律上下摆 | 组心间距按两组带子的实际半宽/半高算；横屏左右摆、竖屏上下摆 |
| 未收藏的虚线小方块"孤零零挂在角落"，看不出是谁引用的 | 引用边用的是 `--border`（`#d1d9e0`），白底上等于隐形 | 灰阶提到 `--fg-subtle`，线宽保底 1.3px；幽灵节点描边同步加深 |
| 点一个节点，图会自己挪一下，再点第二个就点不中 | `highlight()` 把 `alpha` 拉到 0.18，等于每点一次就跑一遍力导向 | 选中只改绘制状态，不碰物理 |
| 连线上的「规范 2 / 信息 1」小到看不清 | 字号写成了 `min(10, 9/k)`，被 `k` 除反了 | 改成 `9.5/k`，屏幕上是稳定的小字 |
| 手机上图和带子挤成一团 | 竖屏画布只有 390px 宽，两条带子必然重叠 | 画布高度提到 `clamp(300px, 54vh, 460px)`；窄屏（<520px）不画分组带，只留彩色节点 + 图例；全屏按钮仍在 |
| 查路径里输入 `green-terminology`（界面上显示的短名）却"认不出" | 解析只认 `draft-ietf-green-terminology` 这种全名 | 允许去掉 `draft-` / `ietf-` 前缀后唯一命中；`RFC 9000` 允许带空格 |

## 三点五、v0.5：图谱推翻重做（力导向 → 静态分层）

v0.4 之前的图是**自研 Canvas 力导向**。用户的反馈只有一句话，但把问题说透了：

> 「点一下然后就全乱了……这个关系我也看不出来什么关系啊，不直观。」

复盘下来，力导向在这个场景里三个硬伤，一个都改不掉：

| 硬伤 | 为什么改不掉 |
|---|---|
| **布局会动** | 力导向的坐标就是"当前平衡态"。点选要聚拢、全屏要重排、窗口一改又要跑一遍——用户的"点一下就乱"是算法的本性，不是参数没调好 |
| **看不出方向** | 弹簧没有方向感，"谁引用谁"全靠箭头贴在线中间，密集处根本找不到箭头 |
| **没有层次** | IETF 引用是 DAG（有明确的"地基 / 上层建筑"关系），力导向把它压成一个匀质的毛球 |

于是整页推翻，改成**业界知识图谱最朴素的那种**：固定的点、固定的边、能看出方向。

### 管线（离线算坐标，运行时只画）

```
snapshot.json.gz ──scripts/layout.py──▶ app/data/layout.json ──kg.js──▶ SVG
                     ① 抽主干子图            ② rank（graphviz dot）      ③ 网格化 + 取景
```

1. **抽主干子图**：组内最多 32 份。不是"取前 N 个"——从被引最多的 6 份出发、沿引用边 BFS 走 3 步，
   取连通最密的那一圈。**没有任何边的孤立文稿不入图**（它们只是列表，不是图）。
   这样图里每一根线都有意义，而不是一片谁和谁都不挨着的散点。
2. **层次**：`dot -Tplain` 用 `rankdir=TB` 求 rank，rank 0 是地基。
3. **网格化（前端）**：rank → 行，层内按 dot 的次序排开。一层里点太多就折成"子行"，
   层与层之间永远留一条 34px 的空带——这条带子是"能看出层次"的关键。
4. **取景**：先按估算铺满，再**量真实墨水盒**（`getBoundingClientRect`），把溢出比例一次性折进缩放，
   最后按真实包围盒居中。桌面 28 领域实测：文字重叠 0 处、文字压点 0 处、越界 0 处。

### 可读性的几条硬规矩

| 规矩 | 原因 |
|---|---|
| 圆点在上、标签挂在点下方两行 | 同样是"点 + 字"，框内写字必然和邻居打架；字挂在格子里、行高 60px，才排得下 |
| 同一行内右推避让（按标签实测宽度） | 长名（`netconf-http-client-server`）会把邻居的字压掉；按宽度逐列右推，绝不叠字 |
| 边从圆的左右两侧出发、中线处上下分道 | 十几条边叠成一根就什么也看不出来；分 5 条道后能数清"有几条" |
| 点选只切 class，**不动坐标** | "点一下全乱"是上一版最大的怨言，这条是红线 |
| 聚焦模式：非邻居淡到 6% 且隐藏文字 | 高亮十几条线反而糊成一团，看不出"它到底依赖谁" |
| 全屏是**真全屏**，且**上下**排 | 页眉页脚一起收起（`body:has(.kg-page.is-fs) > header/footer {display:none}`），Esc 退出。全屏时图在上、说明在下并各自滚动——左右并排（尤其手机上）会把图挤成一条竖缝，图反而看不见了；说明区限高 26vh，不抢图的高度 |
| 下拉里只放**我收藏的组** | 图谱按工作组组织，全站几十个组绝大多数跟我无关。只列"我收藏的草案所属的工作组"，其余公共组不列——列了也没人看（`?g=` 外部跳转的组临时补进下拉，避免 select 空掉） |
| 无关文案一律删 | 「查路径 / 组间关联 / 文稿间关联」三个子页全部删掉，图下方那堆注释也删掉——图自己说话 |

### 代价（明确接受）

- **不是全量**：一个领域最多画 32 份、最密的那一圈。边缘工作在图里看不到，但一份不丢（右侧列表、搜索、收藏库都在）。
- **不出路径**：不再提供"最短引用链"的交互查询。真要看路径，点节点看"它依赖谁 / 谁依赖它"两跳就够。
- **要重新生成**：`layout.json` 变了就得重跑 `scripts/layout.py`（离线，几秒）。

## 三点六、v0.6：离线正文（按版本下载）

图谱和收藏库解决"读什么"，这一版解决"**没网的时候怎么读**"。

### 为什么不是"给个下载链接"

直接把 `<a href="rfc-editor.org/...">` 甩出去，手机上会跳到浏览器下载目录：文件在，但要另找 App 打开，
读完还得自己去清。所以做成**应用内离线库**：正文存进 IndexedDB，阅读器是应用的一部分，删除也在应用里。

### 三件事

| 能力 | 做法 | 取舍 |
|---|---|---|
| **按版本下载** | 草案用 Datatracker 的 `rev`（如 `34`）往下数到 `00`，`/api/docmeta` 取；RFC 只有一版 | 只列**文本版**（TXT）。HTML 依赖外部 CSS，离线会散架；PDF 要内置解析器，太重 |
| **正文从哪来** | `server.py` 的 `/api/docfile` 转发到 `rfc-editor.org` / `ietf.org/archive` | 浏览器直连会被 CORS 拦，必须同源转发。代理是**白名单 + 正则校验 + 12MB 上限**，不做任意 URL 出口（防 SSRF），不改写内容 |
| **存在哪** | IndexedDB `offline` store：`{id, doc, ver, label, title, bytes, ts, text}` | 一份草案约 400–500KB。列表只读元数据（读完就把 `text` 摘掉），避免几十份正文常驻内存 |

### 阅读体验

- 去掉每页重复的**页眉与 `[Page N]` 页脚**——这是纯格式处理，正文一个字不改。
- 桌面：等宽、限宽 78ch 居中（RFC 本来就是 72 列）。
- 手机：**不折行**，保持 72 列、左右滑动。折行会把居中的标题和悬挂缩进拆散，比横滑更难看。

### 删除与清理

- 删收藏时弹一个三选一：**只移除收藏** / **连同离线副本一起删** / 取消。避免"看不见的垃圾"。
- 收藏库顶部常驻「离线 N 份 · X MB」，点开逐份删。
- 设置页「清空本地数据」把 `offline` 一起清掉，并在确认文案里说明。

### 外链为什么"点了不顺利"

收藏库里的文稿名原本直接外跳 `datatracker.ietf.org/doc/<name>/`。链接本身是对的（实测 200），
但那是 400KB+ 的重页面、还带大量脚本，国内网络下经常转圈。v0.6 先做的是"已离线的直接进阅读器"，
v0.7 索性把外跳整个从主路径上撤掉（见下一节）。

## 三点七、v0.7：一个入口，管版本和本机副本

v0.6 的入口是散的：下载是 `↓`、已下载后变「读」、删收藏是 `×`，三个小按钮挤在文稿名旁边。
用起来乱，且手机上要靠小图标猜。这一版把"这一篇怎么读、要不要存在本机"收进**一个面板**。

| 问题（用户原话） | 改法 | 为什么 |
|---|---|---|
| 下载、删除按钮和链接放一起，显得乱；后面几列很空，第一列局促 | 表格从 6 列收到 4 列：**文稿（名字 + 状态 + 离线标记）/ 标题·笔记 / 被引 / 管理**。笔记并进标题的第二行；列宽从 21% 给到 30%，标题 52%，被引 7%、管理 11% | 一行只留"这是哪篇"和"去哪管它"两件事；状态、离线数都是徽标，不需要各占一列 |
| 下载后按钮变成「读」，不需要 | 名字和「管理」都打开**版本面板**，面板里每个版本一行：`-34 最新 · 已存 465 KB`，底部按当前选中的版本给动作 | 按钮随状态变形，等于让用户记住状态机。面板里"已存/未下载"是**同一行的两态**，看一眼就懂 |
| 点链接时应该先问要看哪一版；选到没下载的，要问是看网页版还是去管理 | 选中未下载的版本 → 底部两个动作：**在线看**（取官方 TXT 但不落库）/ **下载到本机** | "就想现在看一眼"和"要留着断网读"是两种意图，直接给两条路，比再套一层"去管理页"少一步 |
| 打开标准页面还有个「下载原始版本」，点了内容一样，没用 | 阅读器去掉该按钮；本机已存多版时，改为**版本切换器** | 已经在读的内容再下载一份是重复动作；真正缺的是"换一版看" |

### 在线看：不占空间的读法

`#/read?...&live=1` 走同一个 `/api/docfile` 代理，抓到正文直接渲染，**不写 IndexedDB**。
顶栏标「在线」，标题下写明还没存到本机，右上角一个「存到本机」——看完觉得有用再存，比"先下载再说"少一次决策。

### 阅读器只剩两个动作

本机副本：**换版本**（下拉）/ **删除本机**；在线副本：**存到本机**。
「下载原文件」按用户反馈删掉了——正文已经在眼前，再导出一份 .txt 只是把文件丢到手机下载目录里。

### 清理只有一个地方

顶部「离线管理」列出本机所有副本（标题 + 大小 + 日期），每行**阅读 / 删除**，底部**清空全部**。
删收藏时仍然三选一（只移除收藏 / 连同离线一起删 / 取消），但那是另一条路径，不影响这里的批量清理。

## 四、信息架构（v0.3）

第一版做成了「全景地图 + 三大独立页面」，图谱看不出要回答什么；v0.2 收敛成二级菜单，但**默认页仍然靠看图猜**。
v0.3 调整的只有一件事：**把"关系"从图形表达改成可核对的事实清单**，图只作为清单位置感的辅助。

```
图谱（/map）
├─ 我的文稿   ← 默认页，三块清单（每条可点开到证据）
│              ① 直接引用   收藏之间谁引用了谁 / 几条 / 规范还是信息性
│              ② 间接相连   被 ≥2 篇收藏共同引用的第三方文稿（同一技术前提）
│              ③ 跨组依赖   按组看知识流向（你依赖它 / 它依赖你）+ 主技术域
│              画布：按组着色的分区带；带名可读；点带空白处 → 该组详情
├─ 组间关联   以某个组为中心的放射布局：它依赖谁 / 谁依赖它；点邻居换中心，点连线看证据
└─ 查路径     两份文稿 / 两个组的最短引用链；连不上也明确说"不连通"

收藏库（/library）   按 WG/RG 自动归类，每组「已收 / 组内总数」；单列空心组
诊断（/diagnosis）   一张待办清单：① 引用了没读 ② 组里有没收 ③ 过期 ④ 只关注没读
配置（/settings）    域名前缀、主题、LLM 端点、备份；内链数据源与口径
日志（/log）         本地操作日志
帮助 / 关于          概念、口径、法律声明
```

### 关系口径（这是产品的地基）

| 概念 | 判定规则 | 展示方式 |
|---|---|---|
| 直接引用 | 两篇收藏之间存在 Datatracker 的 `refnorm` / `refinfo` / 演进类记录 | 清单行：条数 + 类型 + 方向；点开逐条列出 A→B |
| 间接相连 | 无直接引用，但同一第三方文稿被 ≥2 篇收藏引用（或一方引用、一方被引） | 清单行：`RFC 8341 · 共被 2 篇收藏引用`，点开列出是哪两篇、什么关系 |
| 跨组依赖 | 收藏与外部组之间的 `refnorm` / `refinfo`，聚合成组的 `use / usedBy` | 清单行：角色标签 + 主技术域；点开列 6 条代表性证据 + 组内未收的高被引文稿 |
| 样板规范 | 被引 ≥ 800 次（RFC 2119 / 8174 之类） | 不计入"间接相连"，只在数量里提一句；图谱也不画 |

> 为什么"组"这一级必须有：IETF 的知识分工以 WG 为单位。问"我这些文稿和 eman 有什么关系"，
> 用组聚合才有稳定答案（green 组 → eman 12 条、netmod 15 条、netconf 11 条）；用文稿级最短路径反而噪。

### 为什么砍掉这些

| 砍掉 | 原因 |
|---|---|
| 全量 / 按 Area 浏览 / 密度滑块 | 1481 个活跃组的全景图回答不了任何具体问题；"我的"才是上下文 |
| 6 类缺口 + 覆盖度大卡 | 视野盲区、覆盖度评分属于自我评分叙事；留下四个能当天动手的 |
| 桥梁文稿排行、收藏散布图 | 属于"统计数据"，不属于"我该做什么" |
| 一级菜单 10 项 | 收到 6 项；组间关联 / 查路径降为图谱页的二级菜单 |
| 图谱当主角 | 图只回答"分散在哪几个组"；具体的"是什么关系"交给清单与证据 |

## 五、域名方案

**APP 前缀可改，根域固定为 `ietfmap.app`**（`app` TLD 是 HTTPS-only、语义即「这是一个应用」，适合 PWA；且比 `.com` 更短好记）。

| 候选 | 前缀长度 | 优点 | 风险 |
|---|---|---|---|
| **`atlas.ietfmap.app`** ✅ 默认 | 5 | 语义最强（"IETF 图谱"）、好记、跨语言 | — |
| `map.ietfmap.app` | 3 | 最短 | 略泛 |
| `std.ietfmap.app` | 3 | 偏"标准"语义 | 与"地图"偏离 |
| `wg.ietfmap.app` | 2 | 强调工作组视角 | 只覆盖容器层 |

**注意（重要）**：`ietfmap.app` 中**同时包含 IETF 缩写和 Map 通用词**，仅作描述性使用尚可，但**不能**做官方暗示。上线前须：
1. 页面常驻 **"Unofficial · not affiliated with the IETF Trust"** 声明（已在页脚与关于页落地）；
2. 避免使用 IETF 的 Logo/菱形标志/规范字体外观作为品牌标识（本项目用纯文字 + 自有配色）；
3. 不使用 `ietf.org` 子域、不模仿 Datatracker 视觉；
4. 见 `docs/LEGAL.md` 的措施清单。

## 六、技术选型

- **纯静态 PWA**（无后端）：可部署到任意静态托管（Cloudflare Pages / Netlify / GitHub Pages），零运维、零数据收集。
- **零构建依赖**：原生 ES Modules + IndexedDB + Service Worker，无框架。原因是雏形要能「直接发布」，构建链越短越可靠。
- **图谱渲染**：v0.5 起为**静态分层 SVG**——布局离线用 `graphviz dot` 求 rank（`scripts/layout.py` → `app/data/layout.json`），
  运行时约 300 行原生 SVG 只按坐标画点与箭头。弃用力导向的原因见 §3.5。
- **数据**：构建期从 datatracker 拉取快照（`scripts/fetch.py`），产出 `data/snapshot.json`，随应用一起被 SW 缓存。

### 待观察的取舍

- **间接相连的阈值**：目前"被 ≥2 篇收藏共同引用"就上榜。收藏规模到 30+ 时可能需要提到 ≥3，并引入
  "该文稿在你的收藏里出现的组跨度"。目前样本太小，先不调。
- **技术域关键词**：`DOMAINS` 是一组正则，覆盖 YANG / NETCONF / MIB / 安全传输 / 标识注册 / 流程指南。
  新增技术栈（如 AI 相关、卫星）时要补；漏判会落到"其他"，不会丢数据。
- **LLM 层**：仍是可选的、带证据编号约束的归纳，不参与"有没有关系"的判定——判定只认 Datatracker 的引用记录。
